## PR description (kk7ds/chirp, branch dm32uv-port-timeout)

Title: `dm32uv: Don't change the serial timeout before every read`

As you spotted on #1656, the driver set `pipe.timeout` before every read. On Windows,
pyserial applies that by reconfiguring the open port (`SetCommTimeouts` plus a full
`SetCommState`), and the driver did it right after sending each command, while the radio
may already be replying. That fits #12652: FTDI cables fail at a random point with a
"Bad reply" error, while Prolific cables and the vendor software work.

`sync_in()` and `sync_out()` now set `pipe.timeout` once, to 5 s, before any traffic, and
every reply is a single `read(n)`. The per-read timeouts and the read loop are gone. 5 s
covers a 4 KB page and the ACK after a page write with a wide margin; a short read means
something went wrong and stops the transfer, as before.

Tested with the driver tests and my simulator (a download and an upload set the timeout
once each and never during the transfer). I can't test Windows here (Linux, FTDI), so I'm
asking the reporter on #12652 to try it with "Load module from issue" before this is
merged. That's why it says "Related to" rather than "Fixes".

## Reply on chirpmyradio.com #12652 (attach the fixed `baofeng_dm32uv.py`)

Hi John, I'm the author of the DM-32UV driver. Thanks for the detailed report, and to Dan
for the pointer.

Dan's suspicion fits what you're seeing. The driver changed the serial port's timeout before
every read. On Windows that reconfigures the port each time, while the radio is already
sending its reply, and some USB serial drivers (apparently FTDI's) can lose bytes when that
happens. That would give exactly what you describe: a different "Bad reply" error at a
different point each time, with only some cables. The factory software sets its timeouts
once, which is why it works with both.

I've attached a fixed driver that never changes the timeout. Could you try it with your FTDI
cable before it goes into a CHIRP build?

1. In CHIRP, turn on Help → Developer Mode and restart CHIRP.
2. File → Load module from issue, enter 12652, and pick `baofeng_dm32uv.py`.
3. Download from the radio with the FTDI cable, a few times if you can.

If it still fails, please do Help → Report or update a bug → Existing bug 12652 straight
after a failure, as Dan described, so the log and serial trace show the failing session.

One more thing from your log: your radio has firmware DM32.01.L01.048, and I developed the
driver on .047. Your Prolific downloads worked, so it doesn't look like the cause, but it's
good to know.
